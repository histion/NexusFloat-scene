## v1.9.0：充电统计 + 使用统计（对标 Scene）并打包 APK

### 需求
1. 充电统计功能，带充电图和各类数据统计
2. 类似 Scene 的「本次充电后到下次充电前」使用情况：应用功耗、总亮屏时间、各应用时长、图表
3. 打包成 APK

### 架构决策
- 新增 `com.jj.nexusfloat.stats` 包（Java），采样与存储都在模块 App 进程
- **前台服务**承载采样循环（`specialUse` 类型，不是 dataSync——Android 15 起
  dataSync 一天只给 6 小时）
- 数据落 SQLite（`nexus_stats.db`），三张表：`samples` / `sessions` / `periods`
- 会话与周期的当前状态**不做内存态**：每落一个采样点就把汇总行 UPDATE 一次，
  进程什么时候死都能从 `ongoing=1` 接着算
- 功耗归因只能走采样积分（系统不提供逐应用实时电流）；前台时长优先取自
  `UsageStatsManager`（需「使用情况访问」），无权限时退回采样积分
- 唤醒策略：**充电时持 PARTIAL_WAKE_LOCK，放电时不持**。放电期间落点的 `dt_ms`
  封顶到 3 倍采样间隔，避免深睡后一次长间隔被当成「几小时一直在放电」
- 图表自绘（Compose Canvas + TextMeasurer），不引第三方图表库：配色是手写的，
  引库还得再套一层适配

### 踩到的坑（下次直接避开）
- `BatteryManager.EXTRA_CURRENT_NOW` 是 `@SystemApi`，**公开 SDK 里没有**，
  编译报「找不到符号」。改用字面量 `"current_now"` 读 intent extra
- `AppOpsManager.checkOpNoThrow / unsafeCheckOpNoThrow` 返回 **int**（MODE_ALLOWED
  这些），不是 String；SDK 37 里只有 `(String, int, String)` 与 `(int, int, String)`
  两种重载
- Kotlin 属性 `statsEnabled` 会自动生成 `setStatsEnabled`，
  同名的私有方法会撞 JVM 签名（platform declaration clash）→ 方法改名为 `applyStatsEnabled`
- `maxOf(Float, Double)` 无候选，Kotlin 不做 Float/Double 隐式提升
- `startForegroundService()` 后若 `startForeground()` 失败，必须立刻 `stopSelf()`，
  否则系统 5 秒后抛 `ForegroundServiceDidNotStartInTimeException` 杀进程
- SQLite 抽稀不能用 `ROW_NUMBER()`：minSdk 26 的 SQLite 是 3.18，没有窗口函数。
  改用「COUNT 定步长 + `rowid % step = 0`」，rowid 自增顺序即时间顺序

## v8.8.8.8：电流/功率取数修复 + 应用榜补数据 + 记录可删

### 需求（用户实测反馈）
1. 应用使用情况里要显示各应用的**平均功率**、**消耗的电池毫安数**、**百分比**
2. 同时充电和使用时统计不到电流和功率（bug）
3. 充电时功率曲线一直恒 0（bug）
4. 统计页要**永久存储** + **手动删除**单条充电记录 / 单轮使用周期
5. 统计页「屏幕 亮/灭」这个项目没用，去掉
6. 文案：酷安@叶落雨巷 → 酷安@histion自改自用；Github@YeLuoYuXiang → Github@histion；
   版本号 → v8.8.8.8；更新日志加 v8.8.8.8 条目
7. 重新打包，文件名 = 软件名+版本号

### 根因（**这是本次最关键的一条，以后写电池取数务必记住**）
`ACTION_BATTERY_CHANGED` **不含 current_now**。AOSP 的 `BatteryService` 从来不往这个
广播里塞电流，只有 MIUI / ColorOS 等部分 ROM 自己加。上一版只读 intent extra，
所以在原生 ROM 上电流恒 0 → 功率恒 0 → 充电功率曲线恒 0。

**正确姿势：三级取数**（`BatterySampler.readCurrentUa`）
1. `BatteryManager.getIntProperty(BATTERY_PROPERTY_CURRENT_NOW)`（公开 API，主路径）
   —— 失败返回的是 `Integer.MIN_VALUE` 而**不是 0**，必须单独判掉
   —— 再退回 `BATTERY_PROPERTY_CURRENT_AVERAGE`
2. 广播 extra `current_now`（int / long 都试，`getIntExtra` 类型不匹配会静默返回 0）
3. root 直读 sysfs：`/sys/class/power_supply/{battery,Battery,bms,maxfg}/current_now`，
   用 `RootShell.readMany` 批量读（零 fork）。连续失败 5 次就永久放弃，
   否则没 root 的设备每拍白起一次 su

### 其他改动
- `StatsStore.Sample.charging()` 判据从「`currentMa > 0` && 插电」改成
  「插电 && status != BATTERY_STATUS_DISCHARGING」。旧的判据在电流读不到时会把
  插着电的机器显示成「使用中」，而且充电期间不持唤醒锁，曲线会稀稀拉拉
- `queryAppUsage` 增加 `AVG(ABS(power_w))` 作为应用平均功率；`AppUsage` 加
  `avgPowerW` 字段。注意放电样本的 `power_w` 在库里是**负的**（符号表方向），要取 ABS
- 百分比分母用**整机耗电**（`max(period.drain_mah, levelDrop/100*capacity)`），
  不是各应用之和 —— 用后者的话百分比加起来正好 100%，等于宣称后台一点电都不耗。
  分母为 0 时才退回「各应用之和」兜底
- `StatsStore.deleteSession/deletePeriod` 连**汇总行 + 该区间采样点**一起删。
  只删汇总行用户会觉得「删了个寂寞」，而且那些点还在，以后重新扫又会算出来一份。
  进行中的记录不给删（采样线程下一拍会重建，看着像没删掉）
- 新增「使用周期历史」卡片：`periodHistory` 之前只查不显示
- 删除按钮做成「删除 → 确认」两段式，没用系统弹窗（弹窗会打断整页滚动位置）
- 版本号：versionCode `8080808`（只要大于历史 10900 就行，跟 versionName 不必有换算关系），
  versionName `8.8.8.8`

复制改名而来）

## v8.8.8.8 第二轮修复（用户实测回来的三个问题）

### 1. 采样间隔一点就跳到 120 秒卡死
`StatsScreen.StepperRow` 的 `onStep = { onIntervalChange(intervalSec + it) }` 传的是
**新的秒数**（15+1=16），而 `MainActivity.changeStatsInterval(delta)` 是按**步进量**解释的
（`statsIntervalSec + delta * 5`）→ 16×5=80，15+80=95；再点一下变 576 → 夹到上限 120，
之后 `next == statsIntervalSec` 恒成立，只剩「最长 120 秒」的 toast，永远调不动。
**修法**：`onStep = { onIntervalChange(it) }`。
教训：跨 Composable 的回调参数一定要在参数名/注释里写清是「值」还是「增量」。

### 2. 使用周期历史没有删除按钮
`PeriodHistoryCard` 是有了，但只有一条**进行中**的记录时，`if (!p.ongoing)` 把按钮藏了，
用户看到的就是「充电历史能删、使用周期不能删」。
**修法**：进行中的也显示按钮，文案改成「重置」——删掉后采样线程下一拍会重建一条，
语义是「从此刻重新开始记」。`StatsRepository.delete*` 对进行中的记录把区间终点取
**当前时间**（不能用行里那个还在被刷新的 `end_ts`，否则后半段采样点会留下来）。

### 3. 供电功率依旧读不到 —— **最关键的一条**
根因：统计侧自己另写了一套取数，漏了「**本进程直读 sysfs**」这条。
`Constants.Battery` 的注释里早就写着：`BATTERY_PROPERTY_CURRENT_NOW` 在**不少联发科机型
上恒返回 0**（HAL 没实现），而 AOSP 的 `ACTION_BATTERY_CHANGED` 里根本不塞电流。
于是「系统接口 + 广播 extra + root」三条路全断 → 功率恒 0。
监视条能显示是因为它跑在 SystemUI，走的是 `SysfsReader.direct()`（纯 FileReader，
battery 节点多半是 0444），**不需要 root**。

**修法：统计侧直接复用监视条那一整套，不再自己造轮子**
```java
readCurrentA(Intent):
  1. BatteryManager.getIntProperty(CURRENT_NOW) → SysfsReader.parseScaled 判单位
  2. intent extra "current_now"（int / long 都试）→ 同样过 parseScaled
  3. SysfsReader.direct().readBatteryCurrentA()      // 主兜底，不用 root
  4. SysfsReader.root().readBatteryCurrentA()        // 连败 3 次永久关掉，防 su 挂住采样线程
功率: powerTracker.resolve(currentA, voltageV, this::readPowerNowW)   // 与监视条同一个状态机
电压: 广播 extra → SysfsReader.direct()/root() → 兜底 4.0V（voltageMv 记 0 表示未知）
```

**顺带开出去的两个 API**（跨包 package-private 挡住）：
- `SysfsReader.parseScaled(...)` 改 `public static`
- `PowerTracker.resolve` 上一轮已经改 public，`Source` 本来就是 public

**新增电流诊断**：`BatterySampler.currentSourceName()` 暴露这次是从哪条路读到的
（系统接口 / 广播 / sysfs 直读 / sysfs(root) / null），统计设置卡里显示一行。
下次用户再说读不到，就能直接看是「三条路全不通」还是「通了但值不对」，不用翻 logcat。

### 通用教训（本项目通用）
- **同一个物理量不要在两个包各写一套取数**：监视条 (`collector.PerformanceCollector`)
  那套是踩过坑调出来的（联发科恒 0、高通锁死 -10W），统计侧要么复用要么别碰。
- app 进程（untrusted_app）读电池 sysfs：先 `direct()`（FileReader），root 只当最后兜底。
  root 尝试要带失败计数上限，因为 `su` 等授权确认时会把读操作整个挂住。
- 跨进程/跨包复用前先看 `Constants.Battery` 里的注释——那里面写着各机型的坑。

## v8.8.8.8 第三轮：双电芯倍率 + 署名

### 4. 统计页所有功率正好是悬浮窗的一半 —— 双电芯
**根因**：监视条一直在 `PerformanceCollector.collectBatteryData` 里读
`NexusBridge.isDualCellEnabled()`（`Constants.Modules.KEY_DUAL_CELL`），开了就把
**电流和功率同乘 `DUAL_CELL_MULTIPLIER`(2f)**。双电芯机型 `power_supply` 只上报一颗电芯的
读数，所以原始值是实际值的一半。统计侧从采样到展示全程没跟这个开关联动 → 整页功率少一半。
（用户反馈「所有功率都少一半」这个现象，基本可以直接指向双电芯/倍率类问题。）

**修法：读数据时统一缩放，而不是写采样点时乘进去**
- 新增 `StatsRepository.dualCellFactor(Context)`：读同一个 prefs 键，返回 2f / 1f
- 新增 `StatsRepository.applyScale(Dashboard, f)`：在 `load()` 返回前把
  `latest`、两条曲线里的每个 Sample、`currentSession`/`sessionHistory`、
  `currentPeriod`/`periodHistory`、`apps`、`totals`、`appDrainBaseMah`、`capacityMah`
  全部缩放。电流取整 (`Math.round`)，电压**不缩放**（并联电压不变）
- 选读时缩放而不是写时缩放的两个理由：① 不动历史数据；② 用户拨开关整页数字立刻变，
  符合「这是个显示/校准开关」的直觉。写时缩放要等下一拍才生效，用户会以为开关坏了
- 百分比、条形图这些相对量不受影响（分子分母同乘）；`capacityMah` 必须一起缩放，
  否则「电池容量约 xxx mAh」会显示成一半
- `StatsService` 常驻通知上的功率也乘同一个倍率，否则同一瞬间三个地方三个数

### UI
- 统计设置卡新增「双电芯（功率 ×2）」开关，**与监视项目页共用 `dualCellEnabled` 状态和
  同一个回调**（MainScreen 已有 `onDualCellChange`，直接透传给 StatsScreen 即可，
  不用在 MainActivity 新写一份，两页开关永远一致）
- 状态页 `HeaderCard`：版本号徽章和一个新的 `Column(horizontalAlignment = Alignment.End)`，
  署名「原作者：酷安@叶落雨巷」放在 `v8.8.8.8` 正下方

### 注意
`Constants.Modules.DUAL_CELL_MULTIPLIER = 2f`；`KEY_DUAL_CELL = "dual_cell"`，
存在 `Constants.Remote.PREFS_NAME` 里（`saveSwitch` 同时写本地和 Remote prefs）。

## 第七轮（只分析，未改代码）：面板 measured_fps 在骁龙 8 Gen 2 / 8 Elite Gen 5 上无效

用户反馈：FPS 来源「面板 measured_fps」在他的骁龙 8 Gen 2（SM8550）和
骁龙 8 Elite Gen 5（SM8850）上取不到数，要求先给原因分析和可行性。

### 关键外部证据（android.googlesource.com/kernel/msm，sde_crtc.c）
`measured_fps` 不是 AOSP 接口，是高通在 SDE CRTC 上自己挂的，**两代实现差别很大**：

1. **第一代**：sysfs 节点压根不存在，只有 debugfs
   `debugfs_create_file("fps", 0400, sde_crtc->debugfs_root, ...)`
   → 路径形如 `/sys/kernel/debug/dri/<minor>/crtc-<N>/fps`，格式 `seq_printf("fps: %d.%d\n")`
2. **第二代**：新增 `static DEVICE_ATTR(measured_fps, 0444, measured_fps_show, NULL)`
   挂在 `sde_crtc->sysfs_dev` 上，**输出格式是 `scnprintf(buf, PAGE_SIZE, "%d.%d\n", ...)`**
   ——也就是**纯数字 `59.4`，既没有 `duration` 也没有 `frame_count`**
   同时新增 `fps_periodicity_ms`（0644）：**要靠用户空间（显示 HAL）主动写这个节点**，
   `fps_info.fps_periodicity` 为 0 时走「距上一帧的 µs 差」分支，输出会抖/巨大
3. 项目注释里写的 `"fps: 22.7 duration:1000000 frame_count:23"` 是第三个变种（OEM 改动）

→ **结论：候选表/解析要同时能吃三种格式，项目目前确实都能解析**，所以格式不是首要嫌疑；
   首要嫌疑是 **节点路径覆盖不全 + 权限**。

### 定位到的项目侧问题（都还没改）
1. **debugfs 候选路径是错的**：`Constants.Fps.SYSFS_PATHS` 里写的是
   `/sys/kernel/debug/dri/0/measured_fps` 与 `/sys/kernel/debug/dri/*/measured_fps`，
   但第一代实现的实际路径是 `/sys/kernel/debug/dri/<minor>/crtc-<N>/fps`
   —— 少了 `crtc-*` 一层，文件名也是 `fps` 不是 `measured_fps`。有 root 也读不到。
2. **`SysfsReader.expandWildcard()` 静默丢候选**：`parent.list()` 返回 null 时
   `return new String[0]`，整条通配**无声消失**；而 root 通道失败时会退回原 pattern
   （`readAll` 至少试一次）。`/sys/class/drm/*/device/*/measured_fps` 要 list 两层，
   任何一层被 SELinux/权限挡住就整条丢掉，且不留任何日志。
   → 这是「查不出为什么取不到数」的直接原因之一
3. **`readFps()` 的 0 不分「静止」和「读不到」**：面板节点静止时本来就报 0（正常行为），
   于是 `readMeasuredFps()` 清掉 `fpsHit`、`fpsMiss++`，连着 3 拍没命中就进退避
   （`SYSFS_MISS_GRACE=3`，之后每 5 拍才重扫一次）→ 动静切换最多要等 5 拍才恢复。
   同时 `readFps()` 会继续用 `vsync_event` 差分兜底，**「面板来源」报出来的其实是屏幕刷新率**，
   语义已经不一致
4. `FPS_ACTIVE_MIN_FRAMES = 2` 对「内核 1s 窗口只报 1 帧」的情形过严（fps 可能明明合理）
5. v1.8.0 删掉的「探测面板节点」按钮（`PanelProbe`）**类已不存在**，只剩
   `Constants.Fps.PROBE_MAX_RESULTS/PROBE_TIMEOUT_MS` 两个死常量。恢复要重写约 100 行

- 本轮**无任何代码改动、未打包**（用户明确要求先分析）
- 给用户的下一步是「一次现场采集定根因」的命令清单，见 skill
  `.workbuddy/skills/nexusfloat-fps-source-diagnose/SKILL.md`
- 注意术语坑：代码注释里的「骁龙 8 Elite」是 SM8750（第一代 8 Elite），
  **不覆盖 SM8850「8 Elite Gen 5」**——用户报的失效机型正好是后者


## 第八轮（v8.8.9.0）：修面板 measured_fps 取不到数 + 加自检

用户实测反馈：**只勾「面板 measured_fps」时，诊断标记是 `x`**。

### 这条反馈本身的价值
`x` = `TAG_NONE`。面板排全链第一位，只勾它时链尾就停在它身上，而面板失败**不留
zeroTag**，所以最后一定是光秃秃一个 `x`——**分不出「节点不存在」「没权限」
「判成静止」**。这既是用户看到的现象，也说明「缺一个能定位的手段」本身就是个 bug。

### 改了什么
1. **候选表**（`Constants.Fps.SYSFS_PATHS`）：修掉 debugfs 那两条错的
   （原来写 `dri/*/measured_fps`，真实路径是 `dri/*/crtc-*/fps`，少一层且文件名不对），
   补 `/sys/class/graphics/*/fps`、`dri/*/crtc-*/measured_fps`；
   `VSYNC_PATHS` 同步补 `crtc-*/vsync_event`、`vsync_event_sf`
2. **`SysfsReader.expandWildcard` 不再静默丢弃**：`parent.list()` 返回 null 时
   原来 `return new String[0]`（整条候选无声消失），现在退回原模式串返回，
   并用出参 `refused[0]` 标记「被拒」；新增 `MAX_WILDCARD_MATCHES = 64` 防深路径组合爆炸。
   `Channel` 新增 `fpsStage` / `fpsGlobRefused` 两个字段 + 访问器
3. **放宽活跃判据**：`FpsResult.isActive()` 从「只看 frames >= 2」改成
   「frames >= 2 **或** fps 落在 `[FPS_ACTIVE_MIN_FPS(3), FPS_ACTIVE_MAX_FPS(240)]`」。
   下界挡住锁屏 0.7fps 伪活动，上界挡住 periodicity 没被 HAL 写时的乱报值
4. **面板失败细分**：`Constants.Fps.PANEL_FAIL_NO_PATHS/NO_READ/UNUSABLE` = `p1/p2/p3`，
   用字母不用数字以免跟 SF 的 0–9 混（`0x1` 分不出是 SF 还是面板）。
   `PerformanceCollector` 新增 `panelFailStage` 字段（每轮开头重置），
   `fpsFailureStage()` 优先返回它 → 用户看到 `xp1`/`xp2`/`xp3`
5. **`PROBE_FPS_DEBUG` 从 `" 99.9xx"` 加宽到 `" 99.9xxx"`**：p1 是两位标记，
   `clip()` 按探针长度截断，不加宽会把最后一位截掉，诊断就白做了
6. **新增 `collector/PanelProbe.java`**：一键自检——全盘 `find` measured_fps/vsync_event、
   逐条候选展开并分别用本进程/root 试读、列 SELinux AVC 与 enforce 状态，最后给一句结论。
   跑在模块 App 进程（监视条在 SystemUI，uid 不同，所以结论以 root 通道为准）
7. **UI**：`FpsSourceCard` 里在「FPS 诊断」下面加「运行自检」按钮 + 等宽字体结果框
   （`SelectionContainer` 可复制，`heightIn(max=360.dp)` + 竖向滚动），
   用 `withContext(Dispatchers.IO)` 跑。v1.8.0 删掉的两个调试按钮这次以更完整的形式回来了

### 踩到的坑（务必记住）
**Javadoc 里不能出现 `*/`**：我写了 `dri/*/measured_fps`，其中 `*/` 直接终止了块注释，
javac 报一片「非法字符 '\uff0c'」「需要';'」。已验证的排查方式：
`rg '^\s*\*.*\*/.+'`（找 `*/` 之后还有内容的行）。
**写含通配符的路径到注释里时，一律用文字描述代替，不要写完整路径。**

**`File.list()` 返回 null 有两种原因，必须分开判断**（这直接决定 p1/p2 准不准）：
目录**不存在**时它也是 null。第一版实现把两种情况都当「被拒」，结果
`/sys/devices/platform/soc/*/drm/*/...` 这类深路径（绝大多数 soc 条目下没有 drm）
会把 `refused` 污染成 true，`p2`（节点不存在）永远被误报成 `p1`（目录被拒），
整个诊断就白做了。修法：`list()` 为 null 时再判 `parent.isDirectory()` ——
是目录才算「被拒」（返回原模式串 + refused），不是目录就返回空数组。
连接子结果时也要逐个加 + 检查上限，否则「每层各留 64 条」叠起来能到几千条。
