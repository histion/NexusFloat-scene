## 三、帧率取数

这是我在这个模块花时间最多的地方。FPS 有六个来源，各自一个开关，按下面的顺序
依次尝试，取到就停。数值后面会跟一个来源字母（诊断模式），某个来源在这台机器上
不准时，按字母关掉对应的那个就行。

| 顺序 | 来源 | 字母 | 原理 |
| --- | --- | --- | --- |
| 1 | 面板 measured_fps | p | 高通 sde 驱动给每个 crtc 挂的节点，读的时候现算帧率 |
| 2 | SurfaceFlinger latency | b | 走 Binder 直接问 SurfaceFlinger，按 layer 取帧时间戳 |
| 3 | SurfaceFlinger TimeStats | t | dumpsys 里的逐层帧统计，约 1 秒窗口 |
| 4 | FPSGO | g | 联发科内核按进程统计的 queue buffer 帧率 |
| 5 | GED KPI | f | 联发科 GED 模块的逐进程帧率 |
| 6 | Choreographer | x | 只能测到屏幕刷新率，不是应用帧率，仅作兜底 |

### 1. 高通面板节点

高通的 `measured_fps` 有几个坑，都踩过：

- 每个 crtc 都挂一个节点，只有主屏那个是真实读数，其余恒为 0。不能取第一个，
  要把通配展开成具体路径逐个读。
- 主屏 crtc 不一定叫 `crtc-0`。骁龙 8 Gen 3 / 8 Elite 上主屏藏在「外部 crtc」
  下面，路径形如 `/sys/class/drm/card0-sde-crtc-2/device/card0-sde-crtc-0/measured_fps`，
  通配得写到五层深。
- 节点内容是读取时现算的：内核从每帧时间戳的环形缓冲里往前找跨度够 1 秒的那帧，
  帧数除以时间差就是帧率。原版内核输出 `fps: 59.4`，ColorOS / HyperOS 会多带
  `duration` 和 `frame_count`。
- `frame_count` 是「当前时刻往前 1 秒窗口里的帧数」，不是累积器，随读取时机变化。
  早先版本拿它当「面板有没有在出帧」的判据，结果窗口内帧数少于一帧时整个面板方案
  被判死，这就是「p 方案突然不工作」的来源。现在只看 `fps` 字段。

面板读不到时会退回 `vsync_event` 差分：那是内核写的 vsync 中断时间戳，主屏那个非零、
闲置 crtc 恒为 0，两次读数相减就是帧率。

### 2. TimeStats

逐层的帧统计。直接按累计帧数排名会把静止的壁纸、桌面排到前面，所以做了几件事：
启用时先清零统计；只取前 32 层；排除状态栏、监视条自身这类每秒 1 帧的噪声层；
优先匹配前台包名对应的 layer。

## 四、取数开销

监视条每秒读一轮节点。root 通道不用 `cat`。

一开始的写法是常驻一个 `su`，每读一个节点发一条 `cat path`。常驻 su 省掉了 su 自身的
fork，但 `cat` 在 Android 上是 toybox 的软链，每次都要 fork + exec 一次 toybox。
一轮采集扫十几个候选路径，等于每秒十几次进程创建，这才是耗电的大头。

现在改用 shell 内建的 `read`：

```sh
read -r v < /sys/class/.../scaling_cur_freq
```

完全在 shell 进程内完成，零 fork。再把一轮里的所有路径合并成一条命令、一次管道往返
读回来，于是：

| | 旧 | 现在 |
| --- | --- | --- |
| 每轮进程创建 | 十几次 | 0 |
| 每轮管道往返 | 每节点一次 | 一次 |

读不到时按退避策略降低重扫频率：连续 3 轮没命中就转退避，之后每 5 轮真扫一次。
这个 5 轮是从 60 轮降下来的。60 轮意味着锁屏期间退避一路累积，亮屏后要等近一分钟
才恢复出数。

## 五、模块结构

装完之后有两部分在跑。

### 1. SystemUI 进程（被 LSPosed 注入）

- 挂监视条悬浮窗，按屏幕方向、应用白名单、亮灭屏状态决定显示与否
- 自己读 CPU / RAM / 温度 / 部分 GPU 节点
- 隐藏时不只是不可见，采集线程一并停掉

注入走了两条路，互为备份：

- Hook 折叠状态栏 Fragment 的 `onViewCreated`，能直接拿到状态栏的 View 树。
  类名在 Android 各版本里改过多次，所以维护了一张候选表逐个试。
- Hook `Instrumentation.callApplicationOnCreate` 和 `Application.attach`，
  再轮询 `ActivityThread.currentApplication()`。这条路不依赖任何 ROM 类名，
  是 Fragment 全部改名后的保命通道。

### 2. 模块 App 进程

- 用常驻 root shell 读 GPU 频率和占用，读到后写给 SystemUI
- 保持常驻，供 SystemUI 随时取数

SystemUI 里 su 不可靠（SELinux 对 system_server 类进程管得严），所以 GPU 取数放在
普通 App 进程里做。1.8.6 起 SystemUI 侧也会先自己试一次 root 直读，读不到才等
App 进程传，这样重启后 App 进程没起来时 GPU 数据也不会断。

ColorOS 在最近任务里点「全部清除」会把模块进程置为 stopped 状态（等同
`am force-stop`）。这个状态下系统只放行带 `FLAG_INCLUDE_STOPPED_PACKAGES`
的广播，普通广播和 ContentProvider query 都送不到，GPU 数据就会停更。
划卡只是普通杀进程、不置 stopped，所以划卡没事。

「显示时机」里的「后台唤醒」就是修这个的：SystemUI 按设定间隔（默认 15 秒）
发一条带那个 flag 的广播，把模块进程唤醒。设 0 可关闭。

### 3. 设置怎么同步

App 改设置，SystemUI 得知道。三层通道依次尝试：

- RemotePreferences（LSPosed 提供的跨进程 prefs）
- ContentProvider 快照——App 侧把设置写进一个 exported Provider，SystemUI 直接查
- `Settings.Global` 里的 Base64 blob——前两条都不通时由 root 写入

三条都不要求 LSPosed 服务绑定成功，所以 App 界面显示「未连接」时设置照样能生效。

## 七、充电与使用统计（v8.8.9.4）

「统计」页分成**「充电统计」和「使用统计」两个模块**，顶部一个分段控件切换，
一次只看一件事（切换时页面自动滚回顶部）：

- **充电统计**：本次充电曲线（电量—功率 + 电池温度）→ 充电历史 → 累计充电 → 充电统计设置
- **使用统计**：本次使用过程（电量曲线 + 应用图标塔）→ 应用使用情况榜 → 使用周期历史 →
  累计使用 → 使用统计设置

设置项按语义分到两侧：开统计 / 采样间隔 / 常驻通知 / 双电芯 / 电流来源诊断 / 清空数据
属于采样器这套公共设施，放「充电统计设置」；「仅亮屏时记录」「使用情况访问」只影响不充电
时的统计，放「使用统计设置」。

「统计」页在记两件事，互相独立：

### 1. 充电统计

插上充电器就算一次充电会话的开始，拔掉收尾。每次会话记录：

| 项目 | 说明 |
| --- | --- |
| 起止时间与时长 | 会话的首末采样点时间 |
| 充入电量 | 按电流积分（Σ I·dt）累计，不是用电量差反推 |
| 电量变化 | 起止百分比 |
| 平均 / 峰值功率 | 充电时的功率统计 |
| 平均 / 最高温度 | 电池温度统计 |
| 电池容量 | 用「充入电量 ÷ 电量增幅」反推，增幅不足 20% 时不给值 |

曲线有两条：**电量—功率双轴曲线**（电量走左轴 0–100%，功率走右轴）
和**电池温度曲线**。

### 2. 使用统计

拔下充电器到下次插上之间算一个「使用周期」，统计：

- 总时长、**总亮屏时间**、待机时间，配一条亮屏/待机分段占比条
- 电量消耗（%）与耗电估算（mAh）
- 平均放电功率、耗电速度、电量趋势曲线
- **逐应用的使用情况排行**：平均功率、消耗的电池毫安数、占整机耗电的百分比、
  前台时长，带条形图，可在「按耗电 / 按时长」之间切换

前台时长优先取自系统的 `UsageStatsManager`，需要在统计页里授予一次
「使用情况访问」；没授权时自动退回按采样间隔估算，功能照样可用，只是切应用频繁时会偏小。

应用耗电按「该应用在前台期间的放电电流」累计，只能归到前台头上——后台的网络、
推送、定位耗电归不到具体应用，它们留在总量里。所以百分比的分母用的是**这一轮的整机
耗电**，各应用百分比加起来通常不到 100%，差额就是系统与后台。

### 3. 「使用过程」图：折线 + 应用图标塔

使用统计的曲线不是一张普通的折线图——**图里叠了一条应用图标塔**（Scene 的
「使用过程」那种呈现），两者在同一个绘图区、共用同一条时间横轴：

- 绘图区底线上立着一排柱子，每一列是一个等长的时间段
- 柱身里自下而上码着那段时间里在前台的**应用图标**，用得最久的排在最下面，
  越往上越零碎
- **柱子高低＝那段时间的用机强度**，所以整排柱子本身就是一条「用了多少」的波形
- 电量曲线画在塔**上面**（一个是一根亮线、一个是成片的色块，叠起来仍然读得清），
  于是「什么时候在用」「在用什么」「那时候还剩多少电」能对着看

塔下面配了图标图例（用得最久的 8 个应用及各自时长），认不出图标时可以对。图标读不到
（应用已卸载）会画灰块占位，不会整格消失。息屏期间不记前台应用，所以塔上会有空档。

曲线的横轴按**真实时间**排布，不是按采样点序号等距——开着「仅亮屏时记录」时息屏不采样，
按序号排会把那些空洞压扁，曲线、时间标签和图标塔三者就对不上了。

### 4. 记录详情页

充电历史和使用周期历史里的每一条都可以**点进去看那一趟的明细**（返回键或左上角
「‹ 返回」退出）：

| 详情页 | 内容 |
| --- | --- |
| 充电记录 | 起止时间、时长、充入电量、电量变化、平均/峰值功率、平均/最高温度、充电速度，以及从开始充到结束的**电量—功率双轴曲线**和**温度曲线** |
| 使用周期 | 起止时间、时长、亮屏/待机（含分段条）、电量消耗、耗电估算、平均功耗、耗电速度，上面那张**「使用过程」图**，以及这一轮的**应用使用情况**榜 |

充电期间用户多半没在动手机，那段时间的前台应用也没有解释力，所以充电详情只给曲线和
数字，不叠图标塔。

### 5. 采样怎么跑的

- 采样服务是前台服务，通知栏常驻一条实时显示电量 / 功率 / 温度的通知，可以关掉显示
- 采样间隔 5–120 秒可调，默认 15 秒；「仅亮屏时记录」打开后息屏期间不落点，更省电。
  这个开关**充电期间自动关闭**（插着电本来就是全量记录），充电时它在设置里显示为关闭
  并置灰，拔电后自动恢复你原本的选择
- **充电时持唤醒锁**，保证充电曲线够密；**放电时不持锁**，靠定时器和屏幕/电源广播
  触发采样，长时间深睡后落点的积分间隔会被封顶，不会把几小时算成一直在放电
- 数据存本机 SQLite，不联网、不上传；采样明细保留 45 天，充电记录与使用周期**永久保留**。
  历史列表里每条记录都能单独删除（删除会连同该记录时间区间的采样点一起清掉），
  另外还有一键清空；**进行中的记录显示为「重置」**，删掉后从此刻重新开始记这一轮。
  明细过了 45 天的老记录，点进详情页仍能看到全部汇总数字，只是曲线和图标塔没有了
- 电流取数走三条路：`BatteryManager.getIntProperty(BATTERY_PROPERTY_CURRENT_NOW)`
  公开接口 → `ACTION_BATTERY_CHANGED` 的 `current_now` extra → **sysfs 直读** → root 直读。
  只读广播 extra 是不行的：AOSP 根本不往那个广播里塞电流；不少联发科机型的 HAL 也没实现
  `CURRENT_NOW`，所以 sysfs 直读（battery 节点大多是 0444，不需要 root）才是主兜底。
  统计设置里会显示这次实际走的是哪条路，出问题时不用翻日志
- 「双电芯（功率 ×2）」开关在统计设置和监视项目页都有，**读写的是同一个设置**：
  双电芯机型只上报单颗电芯的读数，电流和功率都只有一半，开启后统计页、常驻通知和
  悬浮窗三处的读数会保持一致

## 八、关于空格

监视条默认各项紧贴、不留空格。想在哪里留空，在「项目」页的「空格自定义」里填
「项目名+空格数」，比如 `ZRAM2` 表示 ZRAM 前面加 2 个空格，多个用逗号隔开。

## 九、已知限制

- 联发科没有 `measured_fps` 这类节点，面板来源用不了，只能走 FPSGO / GED / TimeStats
- Choreographer 测的是屏幕刷新率，静态画面下它照样显示 120，不是真实帧率
- 部分 ROM 把 root 节点藏得很深，需要在新版系统上补路径
- 息屏后是否继续显示由「显示时机」里的开关控制，默认关闭
- 统计的应用耗电只算前台期间，后台耗电不计入单个应用；电池容量是反推的估值
